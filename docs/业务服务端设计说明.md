# 业务服务端设计说明

## 1. 模块定位

`business_service` 是本毕业设计中的业务服务端，负责为 Qt 客户端提供独立的业务能力，而不是把所有职责都堆到香橙派边缘推理端。

当前版本已经明确分工：

1. `Python` 主要负责数据处理、模型训练、ONNX 导出。
2. 系统运行阶段的业务能力由 `C++` 服务端承担。
3. Qt 客户端通过 TCP 文本协议访问业务服务端。
4. 业务数据由 `C++ + SQLite` 直接持久化，不依赖 Python 运行时。

## 2. 当前模块职责

当前业务服务端负责：

1. 用户登录校验。
2. 病人信息增加、查询、修改、删除。
3. 病人列表读取。
4. 监测记录保存与查询。
5. 报警记录生成、查询与确认。
6. SQLite 持久化。
7. 兼容首次导入旧版 TSV 数据。
8. TCP 命令服务。

当前业务服务端暂不负责：

1. 病人列表分页、条件筛选与历史检索。
2. 权限细分与多角色鉴权。
3. 多端同步与分布式部署。
4. MySQL / Redis 等更重型中间件接入。
5. HTTPS、TLS、审计追踪等生产级安全能力。

## 3. 当前目录结构

核心代码位于：

- `cpp/src/business/business_service_main.cpp`
- `cpp/src/business/business_logic.h`
- `cpp/src/business/business_logic.cpp`
- `cpp/src/business/file_repository.h`
- `cpp/src/business/file_repository.cpp`
- `cpp/src/business/business_types.h`
- `cpp/third_party/sqlite/`

其中：

1. `business_service_main.cpp` 是服务入口。
2. `business_logic.cpp` 负责协议解析与业务调度。
3. `file_repository.cpp` 负责 SQLite 读写与旧数据导入。
4. `cpp/third_party/sqlite/` 中放置了当前工程使用的 `sqlite3.h / sqlite3.lib / sqlite3.dll`。

## 4. 模块分层

### 4.1 类型层

文件：`business_types.h`

职责：

1. 定义 `User`
2. 定义 `Patient`
3. 定义 `MonitorRecord`
4. 定义 `AlertRecord`

### 4.2 仓库层

文件：`file_repository.h`、`file_repository.cpp`

职责：

1. 初始化业务数据目录。
2. 打开或创建 `business_service.db`。
3. 创建业务表和索引。
4. 提供用户、病人、监测记录、报警记录的 CRUD 能力，其中病人主键为 `patient_id`。
5. 在首次启动时按需导入历史 `TSV` 数据。

当前实现方式：

1. 运行时直接使用 `SQLite`。
2. 旧版 `users.tsv / patients.tsv / monitor_records.tsv / alerts.tsv` 仅作为兼容导入来源。
3. 导入完成后，在线读写统一走 `business_service.db`。

### 4.3 逻辑层

文件：`business_logic.h`、`business_logic.cpp`

职责：

1. 解析文本命令。
2. 校验参数。
3. 调用仓库层。
4. 返回统一响应文本。

### 4.4 服务入口层

文件：`business_service_main.cpp`

职责：

1. 解析启动参数。
2. 初始化日志系统。
3. 初始化 SQLite 仓库。
4. 启动 TCP 服务。
5. 为每个连接处理业务命令。

## 5. SQLite 数据设计

当前运行时数据库文件为：

- `business_service.db`

当前包含四张核心表：

1. `users`
2. `patients`
3. `monitor_records`
4. `alerts`

同时创建以下索引：

1. `idx_monitor_records_patient_id`
2. `idx_alerts_patient_id`
3. `idx_alerts_status`

设计特点：

1. `patients` 是核心主表。
2. `monitor_records` 和 `alerts` 通过 `patient_id` 关联病人。
3. 开启外键约束，删除病人时会级联删除对应监测记录和报警记录。
4. 报警确认状态通过 `status / confirmed_at / confirmed_by` 保存。
5. 病人信息修改只更新非主键字段，当前不支持直接修改 `patient_id`。

## 6. 当前协议设计

当前采用按行文本协议，每条命令以换行结束。

### 6.1 已支持命令

1. `PING`
2. `LOGIN <username> <password>`
3. `LIST_PATIENTS`
4. `GET_PATIENT <patient_id>`
5. `ADD_PATIENT id|name|gender|age|phone|remark`
6. `UPDATE_PATIENT id|name|gender|age|phone|remark`
7. `DELETE_PATIENT <patient_id>`
8. `ADD_MONITOR_RECORD patient_id|pred_label|confidence|alert_level|latency_ms|source|sample_name|true_label`
9. `LIST_MONITOR_RECORDS <patient_id>`
10. `LIST_ALERTS <patient_id>`
11. `LIST_ALL_ALERTS`
12. `CONFIRM_ALERT alert_id|confirmed_by`
13. `QUIT`

### 6.2 默认管理员账号

首次启动会自动生成默认账号：

- 用户名：`admin`
- 密码：`123456`

## 7. 旧版 TSV 兼容策略

为了不丢失前一阶段已经生成的测试数据，当前仓库层保留了首次导入逻辑：

1. 如果 SQLite 目标表为空，并且同目录下存在旧版 TSV 文件，则自动导入。
2. 导入来源包括：
   - `users.tsv`
   - `patients.tsv`
   - `monitor_records.tsv`
   - `alerts.tsv`
3. 导入完成后，后续业务读写统一落到 `business_service.db`。

这意味着：

1. 老数据可以迁移进来。
2. Qt 上层协议不用改。
3. Python 不再参与运行时业务存储。

## 8. 当前版本的意义

这一版的意义不再是“先搭骨架”，而是已经把业务服务端的在线持久化真正落地到了 C++ 运行时中，并补齐了病人信息修改能力。

你可以对老师这样表述：

```text
当前系统的业务服务端已经由 C++ 直接接入 SQLite，完成了登录、病人管理、监测记录、报警记录与报警确认等在线持久化能力；其中病人信息支持在 Qt 客户端完成新增、修改、删除。旧版 TSV 数据保留首次导入兼容。Python 主要用于模型训练与数据处理，不参与系统运行阶段的业务存储。
```
